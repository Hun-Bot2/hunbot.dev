이번에는 기능을 추가하지 않았다. 대신 이미 있던 문제를 찾았다.

> 화면을 봐서는 아무 문제가 없었다. 세어보니 문제가 있었다.

이 글은 그 과정을 정리한 것이다. 다음 글에서는 구조를 어떻게 바꿨는지 쓴다.

## 1. 초안 37개가 공개되어 있었다

블로그 목록 페이지를 열면 글이 87개 있었다. 그런데 실제로 발행 가능한 한국어 글은 50개였다.

원인은 단순했다. 초안을 걸러내는 코드는 `src/utils/blog.ts`의 `getAllPosts()` 하나뿐인데, **어떤 페이지도 그 함수를 부르지 않고 있었다.**

```ts
// 초안을 거르는 유일한 곳
export async function getAllPosts() {
  const posts = await getCollection('blog', ({ data }) => !data.draft);
  return sortPostsByDateDesc(posts);
}
```

블로그 목록, 홈, 카테고리, 태그, 글 상세까지 8개 라우트가 전부 `getCollection('blog')`를 필터 없이 그대로 호출하고 있었다. `draft: true`를 붙여도 아무 효과가 없었다는 뜻이다.

### 더 나빴던 점

RSS와 sitemap은 초안을 **제대로** 걸러내고 있었다.

그래서 초안들은 *읽을 수는 있지만 색인은 안 되는* 상태였다. 피드에도 안 나오고 sitemap에도 없으니, 내가 가진 어떤 점검 수단으로도 보이지 않았다. 그런데 블로그 목록을 연 사람에게는 그냥 보였다.

문서(`CLAUDE.md`)에는 "`draft: true`는 모든 목록과 sitemap, RSS에서 글을 제거한다"고 적혀 있었다. sitemap과 RSS에 대해서는 사실이었고, 목록에 대해서는 사실이 아니었다.

## 2. 찾은 방법은 '보는 것'이 아니라 '세는 것'이었다

스크린샷을 아무리 봐도 이건 안 보인다. 87개가 보기 좋게 잘 렌더링되고 있었으니까.

렌더링된 개수와 소스의 개수를 비교했더니 바로 나왔다. 87 ≠ 50.

이 방법은 앞으로도 쓸 만하다고 생각해서 규칙으로 적어뒀다.

> 렌더링된 총계와 소스의 총계를 비교할 것. 개수가 안 맞으면 필터링 버그이고, 그건 화면상으로는 절대 버그처럼 보이지 않는다.

고친 뒤에는 재발 방지 장치를 붙였다. `src/pages/` 아래 파일이 초안 필터 없이 블로그 컬렉션을 읽으면 빌드를 실패시키는 검사를 추가했고, 일부러 잘못된 파일을 하나 만들어서 실제로 실패하는지 확인했다.

## 3. frontmatter는 '형태'만 검사하고 있었다

두 번째 문제는 더 미묘했다.

14개 파일이 **완전히 똑같은** frontmatter를 가지고 있었다. 템플릿을 복사하고 내용을 안 바꾼 것이다.

```yaml
title: '26년 반기를 돌아보면서'
description: '설명 입력'
pubDate: '2026-06-12'
tags: ['tag1', 'tag2']
category: 'category'
series: 'series 이름'
```

이 중 13개가 같은 제목으로 발행되고 있었다.

### 왜 아무것도 못 잡았나

Zod 스키마는 **형태**를 검사하지 '의미'를 검사하지 않는다. `['tag1', 'tag2']`는 문자열 배열로서 완벽하게 유효하다. `category: 'category'`도 문자열이니 통과한다.

더 나빴던 건 `CATEGORY_ALIASES`에 이런 줄이 있었다는 것이다.

```ts
'category': 'misc',   // 플레이스홀더를 실제 카테고리로 취급하고 있었다
```

플레이스홀더를 정상 값으로 **정당화**하고 있었다. 이 줄은 지웠다.

### 2단계로 막았다

1. **사이트가 자동으로 제외한다.** 초안이 아니고, 템플릿 값이 없고, 같은 언어·제목·날짜가 겹치지 않아야 발행된다.
2. **검사기는 경고만 한다.** 빌드를 실패시키지 않는다.

빌드 실패로 만들지 않은 이유가 있다. 1번이 이미 사이트를 보호하고 있으므로, 실패시키면 14개 글을 다 고치기 전까지 아무 작업도 못 하게 된다. 지금은 `npm run content:validate`를 돌릴 때마다 제외된 파일과 이유가 목록으로 나온다.

게이트는 파일을 **숨길 뿐 고치지는 않는다.** 그 글들이 실제로 무슨 내용이어야 하는지는 내가 정할 문제지 자동화가 정할 문제가 아니다.

## 4. 내가 만든 규칙이 틀렸던 부분

처음에 "설명이 10자 미만이면 플레이스홀더로 간주"하는 규칙을 넣었다.

그랬더니 멀쩡한 글 두 개가 같이 숨겨졌다. `Santander Product Recommendation 01`은 제목도 태그도 카테고리도 시리즈도 전부 제대로 있는데, 설명이 `'필요한 정리'`로 짧다는 이유만으로 배제됐다.

짧게 쓰는 건 취향이지 결함이 아니다. 그리고 글을 안 내보내고 싶으면 이미 `draft: true`가 있다.

그래서 길이 규칙은 지우고, 정확히 일치하는 템플릿 문자열만 잡도록 바꿨다. 한국어 글 기준으로 34개에서 36개로 돌아왔다.

## 5. 깨진 내부 링크 8개

링크 검사를 돌리니 8개가 깨져 있었는데, 두 종류가 섞여 있었다.

**6개는 초안을 가리키고 있었다.** 초안이 새어나가고 있을 때는 '작동하는 것처럼' 보였던 링크들이다. 초안을 발행하는 건 별개의 결정이라, 문장과 라벨은 그대로 두고 링크만 평문으로 바꿨다.

**2개는 실제로 존재하는 글을 잘못된 형식으로 가리키고 있었다.** `[llm-service-kr02.mdx](./llm-service-kr02.mdx)`처럼 URL이 아니라 파일 경로를 적어둔 경우였다. 이건 제대로 된 URL로 고쳤다.

지금은 내부 링크 9,574개가 전부 유효하다.

## 6. 검사기 27개가 아무도 안 돌리고 있었다

이게 사실 제일 큰 문제였다.

이 저장소에는 SEO, 라우트, 링크, CSP, 접근성, 성능 예산, 콘텐츠까지 검사하는 스크립트가 27개 있다. 개인 블로그치고는 꽤 잘 갖춰진 편이다.

그런데 **CI가 없었다.** 린터도 포매터도 없었다. 누가 기억해서 직접 돌릴 때만 돌아갔다.

초안 유출 문제도 꽤 오래 살아 있었는데, 기존 검사기를 CI에서 돌리기만 했어도 생긴 날 바로 잡혔을 것이다. 그래서 GitHub Actions를 붙였다.

- Vercel 런타임과 맞추기 위해 **Node 24** 사용 (로컬은 26이지만 배포 대상에 맞추는 게 맞다)
- 소스 검사 → 테스트 → 빌드 → 산출물 검사 순서. 콘텐츠 오류는 빌드 전에 몇 초 만에 실패한다

링크 검사는 처음엔 "보고만 하고 실패시키지 않음"으로 넣었다. 기존에 쌓인 깨진 링크 때문에 모든 PR이 막히면 곤란해서다. 백로그를 0으로 만든 다음에 게이트를 닫았다. **빚을 먼저 갚고 문을 잠그는 순서**가 맞다고 생각한다.

## 마무리

이번에 고친 것들에는 공통점이 있다.

전부 **재발 방지 장치를 같이 붙였다.** 초안 유출에는 라우트 검사를, 플레이스홀더에는 게이트를, 깨진 링크에는 CI 게이트를 붙였다.

장치 없는 수정은 카운트다운이 붙은 수정이라고 생각한다. 같은 실수를 안 할 거라는 보장이 없으니까.
