앞 글에서 숨어 있던 버그를 정리했다면, 이번에는 구조를 바꾼 이야기다.

> 제약 하나를 먼저 정했다. **클라이언트 자바스크립트 0을 유지한다.** 이건 우연히 그렇게 된 게 아니라 지켜야 할 성질로 취급한다.

측정해보니 160개 정적 페이지에서 JS 청크가 **0개**였고, `_astro`는 176KB인데 거의 전부 CSS였다. 이걸 깨는 변경은 하지 않기로 했다.

## 1. 1페이지와 2페이지가 서로 다른 구조였다

`/ko/blog/`는 글을 **시리즈별로 묶어서** 사이드바와 함께 보여주고 있었다. `/ko/blog/page/2/`는 **시간순 평면 목록**이었다.

번호가 이어지는 한 흐름 안에 완전히 다른 두 설계가 들어가 있었다. 게다가 1페이지에는 다음 페이지로 가는 링크가 **아예 없었다.** 2페이지부터는 생성은 되는데 도달할 방법이 URL 직접 입력밖에 없었다.

시리즈를 주축으로 쓰는 것도 맞지 않았다. 발행 글 50개가 시리즈 19개로 나뉘는데, 그중 **13개가 글 하나짜리 시리즈**였다. 대부분이 1개짜리 그룹인 축은 좋은 축이 아니다.

## 2. 날짜 + 카테고리로 다시 만들었다

역순 시간이 주축이 됐다. 필터는 세 가지다.

- **카테고리** — `normalizeCategory()`가 쓰는 4개 버킷(ai / devlog / review / misc)
- **연도** — 월이 아니라 연도. 2년에 50개면 월 단위는 대부분 빈 칸이 된다. 1개짜리 시리즈와 같은 실수를 반복할 이유가 없다
- **시리즈** — 부축으로 강등. 글이 2개 이상인 시리즈만 노출

상태는 URL 쿼리 파라미터에 저장하고 `localStorage`에 복사한다. 링크를 공유하면 상대도 같은 필터 상태를 본다. 다시 방문하면 마지막 선택이 남아 있다.

중요한 건 **서버가 두 독자를 구분하지 못한다**는 점이다. 모든 글은 서버에서 렌더링되고, 스크립트는 보이기/숨기기만 한다. 계정도 없고 서버 저장도 없다.

자바스크립트를 꺼도 전체 목록이 그대로 보인다. 확인해봤다.

페이지네이션 라우트는 은퇴시켰다. 필터가 전체 목록 위에서 동작하는데 잘라놓은 페이지가 같이 있으면 둘이 계속 어긋난다. URL이 404가 되지 않도록 리다이렉트는 남겼다.

## 3. 익명 피드백: 위험한 절반을 아예 안 만들기

댓글은 Giscus를 쓰는데 GitHub 계정이 필요하다. 계정 없는 사람은 아무 말도 남길 수 없다.

익명 공개 댓글을 만들면 검수 큐, HTML 새니타이저, 더 강한 레이트 리밋, 캡차가 전부 필요해진다. 매일 관리해야 하는 일이 생긴다는 뜻이다.

그래서 **공개하지 않는** 익명 피드백만 받기로 했다.

- `GET` 핸들러가 없다. 웹에서 읽을 방법이 없다
- 저장된 내용은 로컬 스크립트로만 읽는다
- 어디에도 렌더링하지 않는다

이 성질 하나로 검수 큐, 새니타이저, 캡차, XSS 표면이 **동시에** 사라진다. 위험한 절반을 방어하는 대신 아예 만들지 않은 셈이다.

말로만 정한 게 아니라 검사기에 넣었다. `GET` 핸들러가 생기거나 컴포넌트가 피드백을 마크업으로 렌더링하면 빌드가 실패한다.

## 4. 번역은 제안하되 강제로 보내지 않는다

접속 국가로 언어를 자동 전환하는 방법도 있었지만 쓰지 않았다.

IP는 사람이 **어디 있는지**를 말하고, 브라우저 언어는 **무엇을 읽는지**를 말한다. 해외에 있는 한국어 사용자는 한국어를 원한다.

그리고 이 사이트에서는 리다이렉트가 애초에 불가능했다. 한국어 전용 글이 37개고, `academic-reviews`는 한국어만 있고, `404.astro`도 없다. 리다이렉트는 존재하지 않는 페이지로 사람을 보내게 된다. 제안은 그럴 일이 없다.

그래서 `navigator.language`를 보고, **번역이 실제로 존재할 때만** 배너를 띄운다. 닫으면 다시 안 뜬다.

## 5. 이미지: 6.4MB → 0.58MB

`public/images`가 22MB였고 그중 96%가 PNG였다. Astro의 이미지 파이프라인(`astro:assets`)은 **한 군데도 쓰이지 않고 있었다.** 전부 `public/` 경로 문자열이라 포맷 변환도, 리사이즈도, `srcset`도 전혀 없었다.

전체 마이그레이션은 아직 하지 않았다. 콘텐츠 199개 파일이 `/images/...`를 문자열로 참조하고 있어서 이건 컴포넌트 교체가 아니라 콘텐츠 마이그레이션이다.

대신 영향이 가장 큰 파일만 먼저 처리했다. 이미 설치되어 있던 `sharp`로 WebP 변환 + 1600px 리사이즈를 했다.

| | 변환 전 | 변환 후 | 감소 |
|---|---:|---:|---:|
| 대상 7개 파일 | 6,419,447 B | 579,370 B | **90.97%** |
| `public/images` 전체 | 23,288,235 B | 17,435,862 B | 5.58 MB |

`AUTO/Car.png` 하나가 1,055KB에서 55KB가 됐다. 67개 중 33개가 1600px보다 넓었다. 어떤 레이아웃에서도 쓰이지 않는 픽셀을 계속 내려보내고 있었던 것이다.

작업 중에 놓칠 뻔한 게 하나 있었다. `otb-chatlist`는 `src/utils/responsive-public-images.ts`에도 키로 등록돼 있어서, 그걸 같이 안 고쳤으면 hero 이미지가 조용히 안 나오게 될 뻔했다.

### 참조되지 않는 이미지 17개

아무 데서도 참조되지 않는데 계속 배포되던 이미지가 17개, 5.28MB 있었다.

한 번에 지우지 않고 분류했다. 그게 맞았던 이유가 있다. "참조 없음"으로 지웠다면 두 개가 잘못 삭제됐을 것이다.

- `CHAT/chatting-media-en.png`는 발행된 한국어 이미지의 **영어판**이다. 영어 글이 아직 없을 뿐이지 죽은 파일이 아니다
- `nanawithme.jpeg`는 몇 시간 전에 진행 중인 작업으로 추가된 파일이었다

결과는 이렇게 나눴다.

- **삭제 132KB** — Astro 스타터 템플릿의 미사용 플레이스홀더 이미지
- **보관 1.85MB** — `archive/images/`로 이동. `public/` 밖이라 더 이상 배포되지 않지만 저장소에는 남는다. 후속 버전이 쓰이고 있는 예전 아키텍처 다이어그램, Zoro UI 개정판들
- **판단 보류 8개** — 그대로 둠

**배포에서 제거된 바이트는 2,074,022 B (1.98MB)**다. 압축으로 아낀 5.58MB와는 따로 적었다. 보관은 바이트를 *옮기는 것*이지 없애는 게 아니라서, 저장소 크기는 1.85MB만큼 그대로다.

하루 기준으로 `public/images`는 22.21MB에서 **14.65MB(-34.0%)**가 됐다.

파일당 600KB 상한은 유지했다. 일부러 큰 파일을 하나 넣어서 검사기가 실제로 막는지 확인했다.

## 6. 디자인 토큰: 이미 있는 걸 승격시키기

CSS를 세어봤다.

| 토큰 그룹 | 사용 횟수 | |
|---|---:|---|
| `--spacing-*` | 48 | 잘 쓰임 |
| `--review-*` (5개) | 48 | 잘 쓰임 — **페이지 지역 토큰** |
| `--home-*` (3개) | 17 | 잘 쓰임 — **페이지 지역 토큰** |
| `--color-*` (전역) | 2 | 죽어 있음 |
| `--surface-panel` 등 | **0** | 죽어 있음 |

하드코딩된 색상은 542개, 토큰 참조는 70개였다.

흥미로운 건 `--surface-panel` 같은 **의미 기반 토큰이 이미 정의되어 있는데 아무도 안 쓴다**는 점이었다. 반면 페이지 안에서 각자 만든 `--review-border`, `--home-muted` 같은 건 잘 쓰이고 있었다. 두 사람이 각자 독립적으로 같은 아이디어에 도달했는데, 전역 토큰은 안 쓰고 지역 토큰은 썼다는 뜻이다.

### 진짜 원인

**라이트 테마가 토큰을 하나도 재정의하지 않고 있었다.**

토큰은 다크 기준 값으로 고정돼 있고, 라이트 모드는 `body.light-theme .어떤클래스 { ... }` 형태의 손으로 쓴 규칙 130개로 구현돼 있었다.

테마에 따라 안 바뀌는 토큰은 색상에 쓸 수가 없다. 그러니 다들 리터럴 값을 쓰고 오버라이드 블록을 따로 쓴다. 하드코딩 542개는 부주의가 아니라 **당연한 결과**였다.

### Stage 0 / Stage 1

새 시스템을 발명하지 않았다. 이미 작동하는 지역 토큰 패턴을 전역으로 올리고, **거기에 테마 인식만 추가**했다.

```css
:root {                    /* 다크 = 기본값 */
  --surface-panel: rgba(255, 255, 255, 0.045);
  --text-primary:  rgb(248, 249, 250);
}

body.light-theme {         /* 같은 이름, 다른 값 — 선택자 오버라이드 없음 */
  --surface-panel: rgba(255, 255, 255, 0.78);
  --text-primary:  rgb(15, 23, 42);
}
```

`global.css`에는 **추가만** 했다(+197 / −0줄). 다른 사람이 같은 파일을 편집 중이었기 때문에, 기존 규칙을 건드리지 않는 게 중요했다.

그리고 컴포넌트 하나(`FeedbackBox`)만 옮겼다. `body.light-theme` 규칙 **9개 → 0개**가 됐고, 토큰 참조 15개가 들어갔다.

### 검증 방법에서 한 번 헤맸다

"보기에 똑같다"는 주장은 확인 가능해야 한다고 생각해서, 요소 7개 × 테마 2개의 계산된 색상값을 변경 전후로 비교했다. 결과는 **14/14 완전 일치**.

그런데 처음 시도한 방법이 틀렸다. 테마 클래스를 바꾸고 같은 실행 안에서 `getComputedStyle`을 읽으면 **전환 애니메이션 중간값**이 나온다. 그래서 한 요소가 계속 이전 테마 값을 보여줬고, 나는 없는 버그를 잠깐 진짜라고 착각했다.

제대로 된 방법은 실제 방문자와 같은 경로였다. 테마를 `localStorage`에 저장하고, **새로고침한 뒤** 측정하는 것.

> 결과가 흔들리는 검증 방법은 없느니만 못하다. 없는 버그를 만들어내기 때문이다.

## 마무리: 숫자가 말해주는 것

| | 아침 | 지금 |
|---|---:|---:|
| `public/images` | 22.21 MB | **14.65 MB** |
| 깨진 내부 링크 | 58 | **0** (CI에서 강제) |
| `body.light-theme` 규칙 | 130 | 126 |
| 하드코딩 색상 | 542 | 709 |

마지막 두 줄은 솔직하게 적어야 한다. 내가 오버라이드 9개를 없애는 동안 필터바 재설계가 30개쯤을 새로 추가해서, 순증감은 거의 없고 하드코딩 색상은 오히려 **늘었다**.

이건 토큰 설계가 실패했다는 뜻이 아니라, 오히려 가장 확실한 근거다. 반나절 동안 토큰 없이 만든 컴포넌트 하나가, 토큰이 없앤 것보다 더 많은 하드코딩을 추가했다. 예측한 그대로 비용이 계속 쌓인다.

Stage 1은 방식이 동작하고 눈에 안 보인다는 것만 증명했다. 실제 이득은 컴포넌트들이 채택해야 나온다.

다음 차례는 `BlogFilterBar`다. 지금 `global.css`에서 가장 크고 가장 최근에 생긴 오버라이드 블록이라, 옮겼을 때 이득이 제일 크다. 편집이 끝나면 바로 시작할 생각이다.
